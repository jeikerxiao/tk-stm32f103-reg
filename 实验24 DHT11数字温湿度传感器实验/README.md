# 实验24 DHT11数字温湿度传感器实验

> 一句话概括：还是那根单总线（PA1），换成 DHT11 一次性把"温度 + 湿度"共 40 位数据吐回来——学会读时序、加校验和，理解为什么这类传感器对微秒延时特别敏感。

## 一、实验简介

- **实验目的**（官方 `readme.txt`）：学习 DHT11 数字温湿度传感器的使用。
  通俗讲：DHT11 内部有一个湿敏电阻 + 一个温度感测元件 + 一颗小 MCU，它把模拟量换算成数字量，
  再用**一根数据线**按固定时序打包发给单片机。单片机要做的，就是"掐着微秒表"把 40 个 bit 一个个听出来。
- **在学习路线中的位置**：
  - 前置：**实验23 DS18B20 数字温度传感器**（同一条单总线、同一套复位/存在脉冲思路，建议先看它）；
    实验4 串口、实验10/11 OLED/TFTLCD（本实验用 LCD 显示结果）。
  - 后续：实验19 IIC、实验21 触摸屏（换成有独立时钟线的总线，你会更清楚"单总线省线、费时"的含义）。
- **开发板与芯片**：正点原子 MiniSTM32 V4，主芯片 STM32F103RC（Cortex-M3，72MHz，256KB FLASH / 48KB RAM）。
  本工程是**寄存器版**：直接读写 `RCC`/`GPIOA`/`SysTick` 等寄存器，不用 HAL/标准库。

> 小概念：**寄存器**就是芯片里一个个可读写的 32 位小格子，"配置外设"＝按手册把对应格子的某几位填成想要的值。

## 二、实验原理

### 2.1 DHT11 是什么样的器件

DHT11 是"**单总线 + 数字输出**"的温湿度传感器，4 个引脚（常见封装）：

| 引脚 | 名称 | 接法 |
| --- | --- | --- |
| 1 | VDD | 3.3V/5V |
| 2 | DATA | 接单片机 IO（本实验 = PA1） |
| 3 | NC | 悬空 |
| 4 | VSS | GND |

特性要点（对照代码里的使用方式）：

| 项目 | DHT11 | 对比 DS18B20（实验23） |
| --- | --- | --- |
| 测量量 | 湿度 + 温度 | 只有温度 |
| 一次数据量 | 40 bit（5 字节） | 暂存器 9 字节，本例只读 2 字节 |
| 数据方向 | **只读**（主机发起始信号，从机回数据） | 可读可写（有 ROM/功能命令） |
| 精度 | 湿度 ±5%RH，温度 ±2℃，**只有整数位有效** | 温度 0.0625℃ |
| 校验 | 第 5 字节 = 前 4 字节求和的低 8 位 | CRC-8（本例未校验） |
| 建议采样间隔 | 手册一般给 ≥1s | 12 位转换最长 750ms |

DHT11 是小数也带的：湿度整数、湿度小数、温度整数、温度小数各 1 字节，再加校验和，共 5 字节；
本工程只用了 `buf[0]`（湿度整数）和 `buf[2]`（温度整数），小数部分被丢弃——这符合 DHT11"小数位基本没意义"的定位。

### 2.2 一次通信的完整时序（编号步骤）

DHT11 的通信永远是"**主机起始 → 从机应答 → 40 位数据**"这三段：

1. **起始信号**：主机把 DQ 拉低**至少 18ms**（代码 `delay_ms(20)`），然后拉高 **10~35µs**（代码 `delay_us(30)`）。
2. **释放总线**：主机拉高后就不再驱动（开漏，线被上拉顶高），把"话语权"交给 DHT11。
3. **应答信号（存在脉冲）**：DHT11 拉低约 **83µs**，再拉高约 **87µs**，然后开始送数据。
   主机只要"等它变低 → 再等它变高"就能判断传感器在不在，这就是 `dht11_check()`。
4. **40 位数据**：从高位（MSB）开始，一位一位送，每位都长这样：
   - **数据 0**：50µs 低电平 + 26~28µs 高电平
   - **数据 1**：50µs 低电平 + 70µs 高电平
   两者前半段完全一样，**区别只在高电平有多长**。
5. **读完 5 字节**后总线释放，等待下一次起始（一次完整传输约 4ms）。

**读一位的巧妙做法**：主机不等"高电平结束"，而是**在上升沿之后固定延时 40µs 再看一眼电平**——
此时如果还是高，说明高电平持续了 70µs，那就是 1；如果已经变低，说明只持续了 26~28µs，那就是 0。
这就是代码里那句 `delay_us(40); if (DHT11_DQ_IN) return 1; else return 0;`。
（对比实验23：DS18B20 是主机在**固定时刻**采样"从机有没有把线拉住"，思路相同、极性相反。）

### 2.3 40 位数据的排布与校验和

| 字节序号 | 内容 | 本工程怎么用 |
| --- | --- | --- |
| buf[0] | 湿度整数部分（%RH） | `*humi = buf[0];` |
| buf[1] | 湿度小数部分 | 读回但丢弃 |
| buf[2] | 温度整数部分（℃） | `*temp = buf[2];` |
| buf[3] | 温度小数部分 | 读回但丢弃 |
| buf[4] | 校验和 = (buf0+buf1+buf2+buf3) 的低 8 位 | 只做比对，不匹配就不更新结果 |

校验代码：

```c
if ((buf[0] + buf[1] + buf[2] + buf[3]) == buf[4])
{
    *humi = buf[0];
    *temp = buf[2];
}
```

这叫**累加和校验**，比 DS18B20 的 CRC-8 弱（换个字节顺序也可能算错），但足够挡掉大部分"时序被打断导致的乱码"。
注意 `uint8_t` 相加会自然截断到低 8 位，所以不用额外取模。

### 2.4 微秒级延时如何实现（本实验的命根子）

DHT11 的 0/1 只差 40µs 左右，延时必须精确到微秒。本工程不用"数指令循环"，而是用 **SysTick 硬件计数器**
（[delay.c](Drivers/SYSTEM/delay/delay.c)）：

1. `delay_init(72)`：`SysTick->CTRL |= (1 << 2)` → 选择内部时钟源 HCLK＝72MHz；
   `g_fac_us = 72`（1µs＝72 个计数）；`SysTick->LOAD = 0X0FFFFFFF` → 24 位递减计数器的最大重载值；`CTRL bit0 = 1` 启动。
2. `delay_us(nus)`：算出需要的节拍数 `ticks = nus * g_fac_us`，进入循环不断读 `SysTick->VAL`，
   把"这一瞬间比上次减了多少"累加到 `tcnt`；计数器减到 0 溢出时会重装，代码用 `tcnt += reload - tnow + told` 补回来；
   `tcnt >= ticks` 时退出。因为直接数硬件时钟，**编译优化、指令条数都不影响精度**。
3. `delay_ms(nms)` 内部就是 `delay_us(nms * 1000)`（本实验起始信号的 20ms 也是这么来的）。

因此：`sys_stm32_clock_init(9)`（8MHz 晶振 ×9 = 72MHz）与 `delay_init(72)` 必须配套，
主频一改，30µs/40µs/83µs 这些时序就全乱。

### 2.5 寄存器版怎么配这根 DQ 线

| 要做的事 | 寄存器 | 本实验填的值及含义 |
| --- | --- | --- |
| 开 GPIOA 时钟 | `RCC->APB2ENR` | bit2（`|= 1 << 2`）＝IOPA |
| PA1 = 10MHz 开漏输出 | `GPIOA->CRL` | 引脚 1 的配置在 bit[7:4]，值为 `0x5`：MODE=01(10MHz 输出)、CNF=01(开漏输出) |
| 拉低/释放 DQ | `GPIOA->BSRR` | 高 16 位写 1 → 复位为 0（拉低）；低 16 位写 1 → 置位为 1（开漏下即"松手"） |
| 读 DQ 电平 | `GPIOA->IDR` | 读 bit1；开漏输出状态下依然能读外部真实电平 |

`dht11_init()` 只配一次输出模式就不再切换方向，靠"开漏 + 读 IDR"实现收发两用；
这也是单总线驱动的通用套路（`sys_gpio_set()` 的 `SYS_GPIO_PUPD_PU` 参数在输出模式下并不生效，
线上默认高电平靠板载外部上拉电阻，见 [sys.c](Drivers/SYSTEM/sys/sys.c) 的函数注释与实现）。

## 五、核心代码解析

### 5.1 起始信号：`dht11_reset()`

```c
static void dht11_reset(void)
{
    DHT11_DQ_OUT(0);    /* 拉低DQ */
    delay_ms(20);       /* 拉低至少18ms */
    DHT11_DQ_OUT(1);    /* DQ=1 */
    delay_us(30);       /* 主机拉高10~35us */
}
```

- `DHT11_DQ_OUT(0)` → `sys_gpio_pin_set(GPIOA, SYS_GPIO_PIN1, 0)` → `GPIOA->BSRR |= (1<<1) << 16`，PA1 被拉低并保持 20ms。
  **这 18ms 以上的低电平是 DHT11 的"唤醒+起始"信号**，短了它不回应答。
- `DHT11_DQ_OUT(1)` 在开漏模式下＝释放总线；30µs 后 DHT11 接管这根线开始回复。
- 函数名叫 `reset`，但它就是"发一次起始信号"，`dht11_init()` 和 `dht11_read_data()` 都会调它。

### 5.2 检测应答：`dht11_check()`

```c
while (DHT11_DQ_IN && retry < 100)      /* DHT11会拉低约83us */
{
    retry++;
    delay_us(1);
}
if (retry >= 100) { rval = 1; }
else
{
    retry = 0;
    while (!DHT11_DQ_IN && retry < 100) /* DHT11拉低后会再次拉高约87us */
    { retry++; delay_us(1); }
    if (retry >= 100) rval = 1;
}
```

两段"最多等 100µs 的轮询"，正好覆盖手册的 83µs 低 + 87µs 高（第二段的 87µs 上限留得偏紧，
若模块个体差异大可能判超时，这是本驱动经验值）。返回 0 = 有应答，1 = 没接好/时序不对。
`dht11_init()` 的返回值就是它，所以 `main()` 里 `while (dht11_init())` 就是在"没检测到就一直报错重扫"。

### 5.3 读一位：靠 40µs 采样点区分 0 和 1

```c
uint8_t dht11_read_bit(void)
{
    uint8_t retry = 0;

    while (DHT11_DQ_IN && retry < 100)  /* 等待变为低电平 */
    { retry++; delay_us(1); }

    retry = 0;
    while (!DHT11_DQ_IN && retry < 100) /* 等待变高电平 */
    { retry++; delay_us(1); }

    delay_us(40);       /* 等待40us */

    if (DHT11_DQ_IN) { return 1; }
    else { return 0; }
}
```

- 第一个循环等 50µs 低电平结束，第二个循环等上升沿出现；两个循环各有 100µs 超时上限，防止传感器掉线时死等。
- 关键就一句 `delay_us(40)`：**在上升沿后 40µs 采样**。数据 0 的高电平只有 26~28µs，此时已回低 → 返回 0；
  数据 1 的高电平有 70µs，此时仍是高 → 返回 1。40µs 正好落在两者中间，容错最大。
- 顺带一提：这个函数没有 `static`（同文件的 `dht11_read_byte` 有），但仍没在头文件里声明，外部用不到，属于风格瑕疵。

### 5.4 读字节与读数据：高位在前 + 校验和

```c
static uint8_t dht11_read_byte(void)
{
    uint8_t i, data = 0;
    for (i = 0; i < 8; i++)         /* 循环读取8位数据 */
    {
        data <<= 1;                 /* 高位数据先输出, 先左移一位 */
        data |= dht11_read_bit();   /* 读取1bit数据 */
    }
    return data;
}
```

DHT11 **高位（MSB）先出**，所以每读一位先把 `data` 左移再塞进最低位——与实验23 DS18B20 的 `data |= b << i`（低位先出）相反，
这是两个传感器最容易写错的地方。

```c
uint8_t dht11_read_data(uint8_t *temp, uint8_t *humi)
{
    uint8_t buf[5];
    uint8_t i;
    dht11_reset();

    if (dht11_check() == 0)
    {
        for (i = 0; i < 5; i++)     /* 读取40位数据 */
        {
            buf[i] = dht11_read_byte();
        }
        if ((buf[0] + buf[1] + buf[2] + buf[3]) == buf[4])
        {
            *humi = buf[0];
            *temp = buf[2];
        }
    }
    else
    {
        return 1;
    }
    return 0;
}
```

- 只有**校验和通过**才写 `*humi / *temp`；校验失败时函数仍返回 0（只有"没应答"才返回 1），
  而 `main.c` 连返回值都没用 → 校验失败的这一次会**把上一次的旧值继续显示在屏幕上**，看起来"数字不动"。
  这是排查"读数卡住"时的第一嫌疑点。

### 5.5 主循环显示

```c
dht11_read_data(&temperature, &humidity);               /* 读取温湿度值 */
lcd_show_num(30 + 40, 130, temperature, 2, 16, BLUE);   /* 显示温度 */
lcd_show_num(30 + 40, 150, humidity, 2, 16, BLUE);      /* 显示湿度 */
```

模板串 `"Temp:  C"` / `"Humi:  %"` 先把冒号后面的位置占好，`lcd_show_num(..., 2, ...)` 固定显示 2 位整数
（`lcd_show_num` 会用空格吞掉前导 0），所以显示形如 `Temp:  28 C` / `Humi:  65 %`。

## 七、实验现象

1. 上电后 LCD 显示 `STM32` / `DHT11 TEST` / `ATOM@ALIENTEK`。
2. **没插 DHT11 或插反**：第 4 行反复闪现 `DHT11 Error`，程序卡在 `while (dht11_init())`。
3. **插好 DHT11**：显示 `DHT11 OK`，接着两行 `Temp:  C` / `Humi:  %` 里的数字每约 100ms 刷新一次。
4. 对传感器**哈一口气**：湿度先明显上升（几十秒内可到 80~95%），温度也会小幅上升；放到干燥通风处后缓慢回落。
5. 用手捏住探头：温度上升（DHT11 温度精度 ±2℃，读数偏"迟钝"是正常的）。
6. LED0（PA8）每 200ms 左右翻转，表示程序在跑。
7. 数值**只会出现整数**，且湿度常见 20~95%、温度常见 0~50℃ 区间内的值；超出范围基本说明读错了或被旧值占位。

## 八、注意事项

- **引脚以代码为准**：官方 `readme.txt` 说 DHT11 在 PG11，代码里是 **PA1**（`DHT11_DQ_GPIO_PIN = SYS_GPIO_PIN1`）。
  本 README 全部按 PA1 讲；改代码前请先确认你板子上传感器座子实际接到哪根线。
- **100ms 采样快于手册建议**：代码每 100ms 起始一次（`if (t % 10 == 0)` + `delay_ms(10)`），
  而 DHT11 通常建议**不低于 1 秒一次**（内部是电阻式感湿体，需要时间恢复）。
  实测能跑，但可能出现连续相同值或跳变；要更稳就把 10 改成 100（≈1s）。
- **校验失败不报错**：`dht11_read_data()` 校验和不匹配时不更新输出、也不返回错误，`main.c` 也没检查返回值，
  所以"数字不动"≠"没在读"。想改进：让校验失败返回 2，并在 LCD 上提示或重读。
- **时序依赖延时精度**：`delay_us(30)`（起始高电平）和 `delay_us(40)`（采样点）是判 0/1 的关键。
  若时钟不是 72MHz、或 `delay_init(72)` 参数写错，会出现"温湿度乱跳/一直是 0"。
- **别在中断里跑这段驱动**：40µs 的采样窗口被中断一插就偏了；移植时请保证这段代码运行在关调度/关中断的短临界区内。
- **上拉电阻**：`dht11_init()` 传的 `SYS_GPIO_PUPD_PU` 在输出模式下不生效（`sys_gpio_set()` 只在输入分支处理上下拉），
  总线空闲高电平由板载外部上拉提供；自己飞线时补一个 4.7k~10kΩ 上拉到 3.3V。
- **读数范围**：`dht11.c` 的函数注释写"温度范围 -20~60°"、"湿度 5%~95%"，
  常见 DHT11 手册标的是温度 0~50℃、湿度 20~90%RH（不带凝结）；驱动里的范围只是提醒性注释，实际以模块手册为准。
- **模块别插反/别带电掰**：官方要求 U4 位置"网面朝外"；调整前先断电。
- **源码是 GBK 编码**：打开源文件请选 GBK/GB2312，否则中文注释乱码（本 README 为 UTF-8）。

## 九、总结与延伸

**本实验要点：**

1. DHT11 单总线流程三段式：**≥18ms 低电平起始 → 83µs 低 + 87µs 高应答 → 40 位数据**。
2. 数据 0/1 的区别在**高电平宽度**（26~28µs vs 70µs），主机用"上升沿后固定等 40µs 再采样"来判定。
3. 40 位 = 湿度整数 + 湿度小数 + 温度整数 + 温度小数 + **累加和校验**；本工程只用整数两个字节，高位在前。
4. 寄存器版依然是那三件套：`RCC->APB2ENR bit2` 开时钟 → `GPIOA->CRL` 把 PA1 配成 `0x5`（10MHz 开漏输出）→
   `BSRR` 写、`IDR` 读。
5. µs 延时来自 SysTick 72MHz 的"时钟摘取法"，这是单总线驱动能成立的物理前提。

**延伸小练习：**

1. 把采样周期改成 1s：`if (t % 10 == 0)` → `if (t == 10)`（配合 `t==20` 清零逻辑自行调整），
   对比连续读数时"湿度回落后不再立刻反弹"的现象。
2. 让校验和生效：在 `dht11_read_data()` 的 `else` 分支返回 2，`main.c` 里判断返回值，
   校验失败就在 LCD 上打一行 `CRC Error`，并统计错误次数经串口 `printf` 输出。
3. 把温湿度分别用两位小数显示：读出 `buf[1]`（湿度小数）、`buf[3]`（温度小数）并用 `lcd_show_num` 补在整数后面，
   观察它们是不是几乎恒为 0——由此理解 DHT11 为什么是"入门级"传感器（可对比 DHT22 的 0.1℃ 分辨率）。
